# 快速模式（预设 `bash-first`）

> **一句话**：模型默认只能调用 bash；只有当这个持久 bash 真的坏掉时，PowerShell 才作为兜底被放出来。
> 名字叫「快速」，快在**每次 shell 调用只花 40–93 ms**，而不是快在功能少 —— 它比标准模式只多不少。

---

## 1. 它解决什么问题

Windows 上 DSH 的默认 shell 是 PowerShell。PowerShell 每一次工具调用都要付出一次
进程/会话握手的地板价：

| 方案 | 每次调用典型耗时 | 相对最初状态 |
| --- | --- | --- |
| 一次性 PS5.1（最初状态） | ~2096 ms | 1× |
| 一次性 pwsh7 | 242–308 ms（trivial）/ 420–520 ms（work） | 8.6× |
| 持久 pwsh7 | 650–900 ms（受 `idleSilence` 地板限制） | ~2.5× |
| **持久 Git Bash（本预设）** | **40–93 ms** | **~35×** |

一次真实会话的基线（会话 `session-09fa564c`，43 次 pwsh）：p50 **675 ms**、p25 615 ms、
总 78.2 s；同样 43 次换成持久 Git Bash 后约 **4–5 s**。

关键点不是「bash 比 pwsh 快」这句笼统的话，而是：**持久 Git Bash 能命中 pwsh 命中不了的
快速路径** —— 它的每次调用落在地板价下沿，而不是被 `idleSilenceMs` 抬起来。

价格上还有一层：一次工具调用就是一个**步**（step），计费按步而非按命令条数。所以本预设同时
引导模型把相关命令**串在一次调用里**（用 `;` 连接只读探测），既省时间也省钱。

---

## 2. 它做什么

- **默认只看得见 `bash`**：`pwsh` 的 schema 被 `agent.ctx.tools.restrict({ deny: ['pwsh'] })`
  真的从工具面移除，**不是提示词劝告**。这一点是被迫的：只写提示词没用，模型仍然看得见 pwsh 的
  schema，第一条 Windows 味道的命令就会伸手去拿。
- **连续失败 2 次后解锁**：解除限制，注入一条 `tool-addition` 开发者消息，并在系统提示挂上
  `## PowerShell fallback unlocked` 段。
- **解锁是单向的**：一次侥幸成功不会把 pwsh 再藏回去。工具面反复横跳会作废请求前缀缓存，
  得不偿失。
- **作用域化、卸载即回卷**：门控是 preset 自己的 `plugins` 里的一个成员，靠作用域父子限定在
  本预设的 agent 上，绝不会泄漏到标准模式；限制本身是 `agent.ctx.effect()` 的 disposer，
  agent 结束就自动拆掉，插件不持有别的状态。
- **它自己不抛错**：加不上限制就只写日志、保持原工具面 —— 降级，但绝不弄坏。

---

## 3. 「失败」怎么算（本预设最要紧的设计点）

持久 bash **不会**在非零退出时报错：`pbash.js` 的 `renderCaptured()` 把
`[Command finished with exit code N]` 追加到**成功**结果里。只看 `result.isError` 会漏。
但反过来，普通非零退出**也不能算失败** —— `grep` 无匹配、`git diff --quiet`、`test -f`
本来就把非零退出当作正常的正确答案，计进去的话两条日常命令就会把 pwsh 放出来，
「bash 专属」这个前提当场作废。

默认只计**shell 本身坏掉**：

| 计入 | 判据 |
| --- | --- |
| ✅ | `result.isError === true` |
| ✅ | `[Command timed out or OOM]` |
| ✅ | `[shell exited: code N]` / `[shell exited]` / `[shell killed by signal: X]` |
| ✅ | shell 被重置、状态丢失（`The persistent bash shell was reset…`） |
| ❌ | `[Command finished with exit code N]`（N≠0）—— 默认**不算** |

注意 `exit 3` 在持久 shell 里产生 `[shell exited: code 3]`：它结束的是 **shell 本身**，
所以算失败。

想要更宽松的「bash 不好使了就放 pwsh」，在门控配置里加 `countCommandFailures: true`
（阈值用 `threshold` 改，默认 2）。

## 4. 能力面：标准模式 + 创造模式

本预设 = **标准模式（`standard`）的全部能力**（33 个成员零丢失）
＋ **创造模式（`cordis` 预设）独有的三项**：

| 并入项 | 效果 |
| --- | --- |
| `tool-cordis` 行 | 解锁 `cordis_inspect_list` / `cordis_inspect_query`（运行时检查） |
| `skill-filesystem.config.customSkillDirs` | 编入三个 Cordis 编写技能 |
| `tool-plugin-manager` 解禁 | 从 `disabled: true` 改为 `!!js "!ctx.get('profileContext')"` |

三项技能分别是 `cordis-composition-reference`、`cordis-plugin-development`、
`editing-cordis-compositions`。

**所以「快速模式」不是精简模式**：它没有为了快而砍能力。唯一被藏起来的是 pwsh 的 schema，
而那是为了避开它的延迟，且失败后会自动还回来。

---

## 5. 怎么用

1. 在 GUI 的 Agent 选择器里选 **快速模式**（预设 id 仍是 `bash-first`，roster 行 id
   `preset-bash-first`，order 5）。
2. **必须新开会话**：预设是启动时绑定的，已有会话保持它启动时的 revision。

适合：Windows 上的日常编码、检索、构建、跑测试 —— 也就是绝大多数会话。
不适合：一开始就必须做 Windows 原生操作（服务、注册表、`Get-*` cmdlet）的会话；
那种情况下 bash 也会很快失败两次，pwsh 会自动放出来，只是多花两次调用的时间。
